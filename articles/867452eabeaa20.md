### 前提: 本プロダクトの技術構成

過去2記事で構築してきた公開基盤を、本題に入る前に軽くおさらいしておきます。

```bash
[ユーザー]
   │ https://miraimirror.app/ ・ /app
   ▼
[Cloudflare プロキシ]（SSL Full (Strict)・Transform Rules でクリーンURL化）
   ▼
[GitHub Pages]（静的ホスティング。GitHub Actions でデプロイ）
   │
   └─ VRM モデル・モーション等の大容量アセットのみ
      [Cloudflare R2]（assets.miraimirror.app）から別途配信
```

- **ホスティングは GitHub Pages**。サーバーサイドを持たない静的サイトで、GitHub Actions のワークフローがリポジトリの内容を `_site/` に集めてデプロイする
- **手前に Cloudflare のプロキシ** を挟み、Transform Rules で `/`・`/app` のクリーンURLを実現（前回記事の内容）
- **大容量アセット（VRM モデル・モーション）は Cloudflare R2** から配信するハイブリッド構成。配信元はホスト名判定で切り替え、ローカル開発ではリポジトリ同梱ファイルを使う

ここで重要になるのが、GitHub Pages の「静的ホスティング専用で、サーバー側の機能をほぼ何も持たない」という性質です。カスタム HTTP ヘッダも設定できなければ、アクセスログの類も提供されません。この制約が、今回のアクセス解析導入の動機と方式選定の両方を左右します。

前回記事の時点で、公開の前提となるタスク（R2 ハイブリッド配信・ファビコン/OGP・クリーンURL化）は消化済みでした。残っていた「必須ではないが公開前にやっておきたい作業」を片付けつつ、「アクセス解析の実計測を本番トラフィックで確認したい」という動機から、正式版に先立つ **β版公開** に踏み切りました。

## 1. アクセス解析の導入

### なぜ入れるか・何を選んだか

GitHub Pages は帯域・訪問数のダッシュボードを提供しません。100GB/月のソフトリミットに対する「現在地」が見えないままの運用は不安ですし、有料クライアントアプリ版の着手判断にも「無料版に定常的な利用があるか」の計測基盤が必要でした。

ツール選定の絶対条件は **Cookie レス・閲覧者識別子なし** であること。本プロダクトは「映像・音声を外部送信しない」をウリにしているため、GA4 のように Cookie で訪問者を識別するタイプのツールを入れて、同意バナーを出すのは世界観に合いません。

比較検討の結果、今回は **Cloudflare Web Analytics** を採用しました。無料で Cookie を使わず、スニペット1行で済み、DNS や R2 と合わせて管理を Cloudflare に一元化できます。

https://www.cloudflare.com/ja-jp/web-analytics/

なお、LP に掲載する「外部送信しない」という訴求文言は、解析導入と矛盾しないよう **「映像・音声（＋トラッキング結果）を外部送信しない」と主語を限定** した表現にしています。アクセス解析・CDN 通信は別レイヤーとしてプライバシーポリシーで開示する形です。

![LPの「プライバシー安心」カード。カメラ映像はすべて端末のブラウザ内だけで処理し、映像が外部サーバーに送信されることはない旨と、マイク（音声）は使用しない旨を記載](https://static.zenn.studio/user-upload/701e92df8cc4-20260814.png)

音声はそもそもマイクを取得しない設計（`getUserMedia({ audio: false })`）なので、こちらはむしろ「マイク不使用」とより強く訴求できます。

### ハマりどころ①: meta CSP があると Cloudflare の「自動注入」は使えない

Cloudflare Web Analytics には、プロキシ済みゾーンなら **エッジで JS スニペットを自動注入** してくれるお手軽モードがあります（公式ドキュメントにも、プロキシ済みサイトでは自動セットアップがデフォルトで有効になる旨が記載されています）。

https://developers.cloudflare.com/web-analytics/get-started/

しかし、GitHub Pages 由来で HTTP ヘッダを設定できず CSP を `<meta http-equiv>` で入れている本サイトでは、エッジで注入されたスクリプトがこの CSP に弾かれてしまいます。つまり **meta CSP 構成ではスニペットの手動設置が一択** です。

:::details 用語メモ：CSP（Content Security Policy）
ページが読み込み・実行できるリソース（スクリプト、画像、接続先など）をホワイトリスト形式で制限するブラウザのセキュリティ機構。通常は HTTP レスポンスヘッダで配信するが、`<meta http-equiv="Content-Security-Policy">` タグでも設定できる。GitHub Pages はカスタムヘッダを設定できないため、本サイトは meta タグ方式を採っている。
https://developer.mozilla.org/ja/docs/Web/HTTP/Guides/CSP
:::

CSP には解析用の2ホストを追記します。

```html
<meta http-equiv="Content-Security-Policy" content="default-src 'self';
  script-src 'self' 'unsafe-eval' https://unpkg.com https://static.cloudflareinsights.com;
  connect-src 'self' https://cloudflareinsights.com;
  img-src 'self' data: blob:; media-src 'self';
  style-src 'self' 'unsafe-inline' https://fonts.googleapis.com;
  font-src https://fonts.gstatic.com;
  base-uri 'self'; form-action 'none'; object-src 'none'">
```

- `static.cloudflareinsights.com` … ビーコン本体の配信元（`script-src`）
- `cloudflareinsights.com` … 計測データの送信先（`connect-src`）

### 実装: 共通ローダー js/analytics.js

LP・アプリ両方の `<head>` で読み込む1ファイルにまとめました。ポイントは2つあります。

- **本番ホストでのみビーコンを読み込む**：localhost や LAN プレビューは計測しない
- **`SITE_TOKEN` が空文字の間は何も読み込まない**：トークン未発行のまま main ブランチにマージしても無害なので、実装 PR とトークン設定の PR を分離できる

```js
// js/analytics.js
(function () {
  const SITE_TOKEN = '4990ceb18b674d9fab9643e8a64d5a2c'; // 公開値（配信HTMLから誰でも見える）

  const isProduction =
    location.hostname === 'miraimirror.app' || location.hostname === 'www.miraimirror.app';
  if (!SITE_TOKEN || !isProduction) return;

  const beacon = document.createElement('script');
  beacon.src = 'https://static.cloudflareinsights.com/beacon.min.js';
  beacon.defer = true;
  beacon.setAttribute('data-cf-beacon', JSON.stringify({ token: SITE_TOKEN }));
  document.head.appendChild(beacon);
})();
```

リファラーの扱いには注意すべき挙動があります。ビーコンは `document.referrer` を読みますが、この値を決めるのは **リンク元ページ側の referrer policy** です。

自サイトには `<meta name="referrer" content="no-referrer">` を入れているため、外部サイトからの流入はリンク元が取れる一方、サイト内の移動（LP → /app）ではリファラーが空になります。

この挙動もそのままプライバシーポリシーに明記しました。実際の文言（「アクセス解析・Cookie」の項）は以下のとおりです。

> 広告は使用していません。利用状況（訪問者数・ページ表示回数など）の把握のため、Cloudflare Web Analytics を使用しています。Cookie は使用せず、閲覧者を識別する情報も保存しないため、個人の特定やサイトをまたいだ追跡は行いません。送信されるのは、閲覧したページのURL・リンク元（外部サイトから来た場合のみ。サイト内の移動ではリンク元を送りません）・ブラウザやデバイスの種類・国・表示速度といった匿名の情報のみです。カメラ映像やトラッキング結果が解析に送られることはありません。

## 2. サイトトークンの発行と設定

Cloudflare ダッシュボード → **Analytics → Web Analytics** でサイトを追加し、発行されたトークンを `js/analytics.js` に貼るだけ……のはずが、ここにも見落としやすいポイントがありました。

### ハマりどころ②: RUM 設定がデフォルトで「自動注入」になっている

プロキシ済みゾーンでは、Web Analytics のサイトが **RUM の自動注入モード**（「有効にする」「有効（EU 内の訪問者データを除外）」）で作られます。

前述のとおり本サイトでは自動注入は CSP に弾かれるため、**「JS スニペットのインストールで有効にする」（手動方式）への切り替え** が必要でした。

![Cloudflare Web AnalyticsのRUM設定画面。「有効にする」「有効（EU内の訪問者データを除外）」「JSスニペットのインストールで有効にする」の選択肢から手動方式を選択している](https://static.zenn.studio/user-upload/627e4a9440b5-20260814.png)

:::details 用語メモ：RUM（Real User Measurements）
実際の訪問者のブラウザで計測を行う方式のこと。合成監視（定点からの自動アクセス）と対になる用語。Cloudflare Web Analytics では、この RUM の計測スクリプトを「エッジで自動注入する」か「サイト側に手動設置する」かを選べる。
:::

なおサイトトークンは配信 HTML に載る **公開値** なので、リポジトリにコミットして問題ありません。API トークンや秘密鍵とは別物で、悪用してもできることは「このサイトの計測として偽ビーコンを送る」だけ。どこに置いても防げない性質のものです。

## 3. ドメイン方針の確定

過去記事では触れていませんでしたが、ドメイン取得時からの懸案がひとつ残っていました。プロダクト名と同名の `miraimirror.jp` が第三者所有だったのです（`.app` を選んだ経緯のひとつでもあります）。

「空いたら取るか」「防衛用に他の TLD も押さえるか」という宿題を、公開前に決着させました。

その `miraimirror.jp` は、JPRS Whois で **Suspended（所有者が更新せず失効プロセス入り）** を確認しました。

```text
[Domain Name]   MIRAIMIRROR.JP
[登録者名]      （空欄）
[Name Server]   （空欄）
[登録年月日]    2024/07/30
[有効期限]      2026/08/31
[状態]          Suspended
[最終更新]      2026/08/01 00:14:34 (JST)
```

更新期限（7月末）を過ぎた 8月1日 0時過ぎに Suspended へ遷移し、登録者情報・ネームサーバーも消えていました。

JP ドメインは失効後およそ1ヶ月で廃止→再取得可能になるため、9月初旬には取れる見込みでしたが、**再取得しない** と判断。防衛併取候補（`.net` / `.moe` / ハイフン版 `.com`）もすべて見送り、**miraimirror.app 1本で運用** することにしました。

### 個人開発だからこそ「リスクを許容して後回し」にできる

防衛ドメインを取らないということは、タイプイン流出（`.com` や `.jp` を打った人が第三者のサイトに着く）や、将来の類似ドメイン取得による便乗・なりすましのリスクを **認識したうえで許容する** ということです。

今回それでよしとしたのは、本プロダクトが個人開発だからです。

- 現時点でユーザー数もブランド価値もこれから。年数千円×複数本の防衛コストに見合うものがまだ無い
- 失効・取得の状況は Whois でいつでも確認でき、スケールしてきた時点で再検討すればよい（後から取れなくなっている可能性は残るが、それも含めて許容）
- 判断と根拠を issue に記録してクローズした。「検討していない」と「検討して見送った」は別物で、後者なら再検討のトリガー（利用者増・収益化）も明確にできる

一方、**仕事などで事業として展開・運用していくプロダクトなら、この判断は逆になる** と思います。

タイプイン流出は機会損失だけでなくフィッシングの土壌にもなり、ブランドが立ってからでは類似ドメインの買い戻しは高くつきます（そもそも売ってもらえないこともあります）。事業プロダクトでは、主要 TLD の防衛取得・類似表記の扱い・失効ウォッチの体制を **公開前に** 検討事項として持っておくべきで、ここが個人開発とのコスト感覚の分かれ目でしょう。

## 4. 公開直前の最終レビューで見つかった公開ブロッカー

公開前チェックリストの「LP 文言・利用規約・ポリシーの最終レビュー」を実施したところ、文言ではなく **構成の重大な不備** が見つかりました。

### ハマりどころ③: CSP の connect-src に R2 ホストが無い＝公開した瞬間モデルが読めない

アプリの meta CSP の `connect-src` に、**R2 のアセット配信ホスト `assets.miraimirror.app` が入っていませんでした**。本番環境ではプリセットの VRM モデル3体と待機モーションをすべて R2 から fetch する構成なので、このまま公開していたら **モデルが1体も読み込めない** ところでした。

![アプリのモデル選択パネル。R2から配信されるプリセットVRMモデルのサムネイル4体が並ぶ](https://static.zenn.studio/user-upload/5670baac61ed-20260814.png)

配信元の切り替えはこうなっています（`js/config.js`）。ローカル開発では空文字＝相対パスなので、この分岐が本番でだけ別オリジンを向きます。

```js
const MM_ASSETS =
  location.hostname === 'miraimirror.app' || location.hostname === 'www.miraimirror.app'
    ? 'https://assets.miraimirror.app/'   // 本番: Cloudflare R2
    : '';                                  // ローカル: リポジトリ同梱ファイルへの相対パス
```

VRM は three.js の GLTFLoader（内部は fetch）で読み込むため、支配するのは CSP の `connect-src` です。修正自体は1ホスト追加するだけでした。

```diff
- connect-src 'self' blob: https://esm.sh https://cdn.jsdelivr.net https://storage.googleapis.com https://raw.githubusercontent.com https://cloudflareinsights.com;
+ connect-src 'self' blob: https://esm.sh https://cdn.jsdelivr.net https://storage.googleapis.com https://raw.githubusercontent.com https://assets.miraimirror.app https://cloudflareinsights.com;
```

### なぜ今まで気づかなかったか

- 本番環境はこれまで「coming soon」表示だけのダミーページ配信で、**アプリ本体が本番ドメインで一度も動いていない**
- ローカル開発では `MM_ASSETS` が空文字＝相対パス（`'self'`）なので、CSP を素通りしてしまう
- 公開前の配信物監査は curl での CORS ヘッダ確認だった。**ブラウザ内で評価される CSP はカバー外**

振り返ると、**本番ドメインで一度も実行されていないコードパスは、CORS・配信物・ライセンスの確認をすべて通していても、CSP のようにブラウザ内で評価される設定のチェックからは漏れてしまいます**。

環境でエンドポイントを切り替える構成（dev＝相対パス / prod＝別オリジン）を使う場合は、切り替え先ホストと CSP のホワイトリストの突き合わせも確認項目に入れておくべきでした。

## 5. β表記の追加と「除去タスクの先行 issue 化」

いきなり正式版ではなく、まずは様子見のβ版として出すことにしたので、その旨をユーザーに見える形で明示しました。

![ヘッダーのワードマーク「Mirai🪞Mirror」の右肩に小さな上付きの「（β）」が付いた表示](https://static.zenn.studio/user-upload/2bf1e0bc7686-20260814.png)

ヘッダーのワードマークには小さな上付きの「（β）」を追加。ワードマーク内に置くことで、グラデーション文字のテキストクリップをそのまま継承する作りです。

```html
<span class="mm-title-name">Mirai<span class="mm-brand-emoji">🪞</span>Mirror<span class="mm-beta-tag">（β）</span></span>
```

```css
/* ワードマーク内に置くので、グラデーションのテキストクリップをそのまま継承する */
.mm-beta-tag { font-size: 0.5em; font-weight: 700; vertical-align: 0.55em; letter-spacing: 0; margin-left: 0.15em; }
```

あわせて、ページタイトル（`<title>`・`og:title`）と `og:site_name` にも「（β）」の表記をつけました。対象は LP・アプリの本体2ページに加え、リダイレクトスタブ2本を含めた計4ファイルです。

β表記は「いつか必ず剥がすもの」です。正式版公開のタイミングで除去作業が発生することは今の時点で確定しているので、そのときの作業タスクにヌケモレが出ないよう、**除去対象の全箇所をファイル別チェックリストとして明示した issue を先に作成してから、β表記の実装 PR を作りました**。

![GitHubのissue「正式版リリース時にβ版表記を除去する」。β表記の実装より先に作成したもの](https://static.zenn.studio/user-upload/c8187447c91a-20260814.png)

表記を追加した本人の記憶が新しいうちに対象箇所を issue に固定しておけば、数週間後の正式版切替時に「どこに（β）を入れたっけ？」と探し直す必要がありません。

## 6. 公開切替

デプロイワークフロー `deploy-pages.yml` の `PUBLISH_MODE` を `comingsoon` → `full` に変更します。

```yaml
# 公開モード
# comingsoon: ダミーページのみ配信
# full:       サイト本体を配信
env:
  PUBLISH_MODE: full
```

デプロイワークフローは `PUBLISH_MODE` を見て `_site/` に集めるファイルを分岐します（comingsoon なら全入口にダミーページ、full なら本体を配置。R2 配信のアセット類は full でも Pages には含めません）。

この coming-soon ゲートは初回デプロイ時に作っておいた仕組みで、切り替えは環境変数1つで済みました。

https://zenn.dev/unsoluble_sugar/articles/a6fb2c3efd5a66#4.-coming-soon-%E3%82%B2%E3%83%BC%E3%83%88%EF%BC%88%E6%AD%A3%E5%BC%8F%E5%85%AC%E9%96%8B%E3%81%BE%E3%81%A7%E3%83%80%E3%83%9F%E3%83%BC%E3%83%9A%E3%83%BC%E3%82%B8%EF%BC%89

マージ → GitHub Actions のデプロイ成功を確認後、curl で配信内容を検証します。

```bash
# タイトル・OGP・noindex・解析スクリプトの確認
curl -s https://miraimirror.app/    | grep -oE "<title>[^<]*|og:(title|site_name)\"[^>]*|noindex|analytics.js"
curl -s https://miraimirror.app/app | grep -oE "<title>[^<]*|noindex|analytics.js|assets.miraimirror.app"

# 解析トークンが配信されているか
curl -s https://miraimirror.app/js/analytics.js | grep "SITE_TOKEN ="

# og:image の疎通確認
curl -s -o /dev/null -w "%{http_code}\n" https://miraimirror.app/models/ogp.png

# R2 の CORS（本番オリジンからの VRM 取得）
```

## 8. 公開後の初修正: 背景画像が等倍表示になるバグ

公開翌日、背景画像をアップロードすると **等倍・左上基準** で表示される問題を修正しました。原因は、CSS では昔からよく知られたショートハンドの仕様でした。

### ハマりどころ④: インラインの background ショートハンドは background-size をリセットする

ステージ背景は動的な値（画像 or グラデーション）を扱うため、インラインで `background: url(...)` を適用していました。

CSS のショートハンドプロパティは **未指定のサブプロパティを初期値にリセットする** ため、クラス側に書いてあった `background-size: cover; background-position: center;` は一度も適用されていませんでした（インライン > クラスの特異性で常に負けます）。

修正はショートハンドの中にサイズと位置を含めるだけです。

```diff
- stageBg: s.bgImageOn && s.bgImage ? ('url(' + s.bgImage + ')') : MM.bgGradient(s.bgColor),
+ stageBg: s.bgImageOn && s.bgImage ? ('url(' + s.bgImage + ') center / cover no-repeat') : MM.bgGradient(s.bgColor),
```

`background: <image> <position> / <size> <repeat>` というショートハンド構文で、`/` 区切りで size を書けるのは position とセットのときだけです。

あわせて、適用されていなかったクラス側の `background-size` / `background-position` は削除しました。残しておくと「ここで cover を指定しているから大丈夫」という誤読を再生産するためです。

「クラスに書いた cover が反映されない」系の現象は、動的スタイルをインラインで当てる構成（React の style 属性など）だと踏みやすいので注意です。

## 学び・ハマりどころまとめ

最後に、今回の作業で得た学びをテーマ別に整理しておきます。

### アクセス解析（Cloudflare Web Analytics）

- **meta CSP 構成では自動注入は使えない**：スニペットの手動設置と、CSP への2ホスト追記で対応する
- **RUM 設定はデフォルトの自動注入から手動方式へ切り替える**：切り替えないと計測されない
- **サイトトークンは空文字ガードつきで実装しておく**：トークン未発行のままマージしても無害になり、実装 PR と設定 PR を分離できる

### 公開前のチェック

- **本番ドメインで一度も実行されていないコードパスは、公開前チェックから漏れやすい**：環境でエンドポイントを切り替える構成では、切り替え先ホストと CSP ホワイトリストの突き合わせを確認項目に入れる

### 公開までの段取り

- **ドメインの防衛取得は「検討して見送った」を記録に残す**：個人開発ならリスクを許容して後回しにできるが、再検討のトリガーは明確にしておく
- **β表記は追加する前に除去 issue を作る**：「いつか剥がすもの」は、追加した時点で全箇所をチェックリスト化しておく
- **公開ゲートを環境変数1つに集約しておく**：公開切替が1行の PR で済む

### CSS

- **background ショートハンドは未指定のサブプロパティを初期値にリセットする**：動的スタイルをインラインで当てるなら `center / cover no-repeat` まで含める
