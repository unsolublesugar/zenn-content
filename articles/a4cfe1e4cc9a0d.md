## はじめに

趣味で投稿しているMikuMikuDance（MMD）動画の作品ポータルサイトを、Claude Design と Claude Code の連携で構築しました。デザイン確定からサイト公開まで約1時間、動画データ140件のフル整備まで実質2日という進め方ができたので、その開発記録を残しておきます。

▼公開中のサイトはこちら

https://unsolublesugar.github.io/mmd-portal/

「なんで作ったの？」「どんなサイト？」という概要編はnoteに書きました。本記事はその技術編として、データ管理の仕組み・埋め込みプレイヤーのハマりどころ・自動抽出の落とし穴など、開発の中身に踏み込んで書きます。

## 作ったもの

ニコニコ動画・YouTube・note に散らばっていた自作MMD動画の情報を一望できる、視聴者向けの公開ポータルです。

![](https://static.zenn.studio/user-upload/0b155864631c-20260725.png)

- シリーズ別・キャラ名タグでの絞り込み、検索、新着順・古い順ソート
- サイト内埋め込みプレイヤーでそのまま再生（ニコニコ / YouTube をタブ切り替え）
- 詳細モーダルに投稿日・note解説記事リンク・お借りした素材のクレジットを掲載
- 縦型ショートは横スクロールレールとして別枠表示

技術構成と実績の数字はこんな感じです。

| 項目 | 値 |
|---|---|
| フロントエンド | ビルド不要の静的サイト（HTML + CSS + JS 3モジュールの計5ファイル・npm依存ゼロ） |
| データパイプライン | Python スクリプト6本（データ生成・CSVインポート・抽出ツール3種・共通処理） |
| 正データ | YAML 140ファイル（1動画=1ファイル・手動編集する唯一の元データ） |
| ホスティング | GitHub Pages（GitHub Actions で成果物を組み立てて公開） |
| 制作期間 | デザイン確定→公開 約1時間、データ140件フル充足まで実質2日 |
| 登録動画 | デザイン工程から引き継いだ50件 → **140件**（未登録90件を発掘・追加） |
| データ充足率 | 再生可能・投稿日・クレジット表記 100%（140/140） |

## 全体の流れ：デザインと実装で環境を分けた

今回の進め方の骨格は「**見た目の意思決定は Claude Design、Git・CI・一括データ処理は Claude Code**」という分担です。デザイン確定後に、仕様・デザイン実体・実データを**ハンドオフ**（実装側への引き継ぎ資料）一式として出力し、Claude Code に渡す流れになっています。

```bash
[Claude Design]
  要件定義 → データ収集 → デザイン2案比較 → ポップ版確定 → 反復調整
   │
   │ ハンドオフ一式を出力
   │  ├─ README.md（実装仕様＋埋め込みの罠）
   │  ├─ 採用デザインのHTML実体（見た目と挙動の正解）
   │  └─ videos.js（実データ50件）
   ▼
[Claude Code]
  /init → Issue化・フェーズ分け → 再実装 → GitHub Pages公開（ここまで約1時間）
  → 抽出ツール実装 → データ50件→140件 → 継続運用の型づくり
```

デザインを固める作業と、それを本番コードに落とす作業は求められる判断が違います。前者を先に終わらせてから後者に渡す流れは手戻りが少なく、ハンドオフ資料に「罠」を書き残したことで再実装時の手詰まりもありませんでした（後述）。

なお、これは今回のように**ゴールが最初から明確で、要件を先に決め切れる**案件だから成立する進め方です。動かしながら要件を探っていくアジャイル的な開発であれば、デザインと実装を行き来する前提で分担を設計するほうが合うと思います。

実際、以前作った資産ポートフォリオダッシュボードでは、Claude Design と Claude Code を行き来して、触りながらブラッシュアップするループを回すパターンでした。

https://zenn.dev/unsoluble_sugar/articles/fd73c7b67d80ce

今回は「自分の作品を並べて見せる」という完成形がブレようのないサイトだったので、決め切ってから一気に組み上げる方式が早いという判断です。

## Claude Design編：デザイン確定までにやったこと

前工程の詳細まで書くと長くなるため、後の実装フェーズに影響した判断だけ絞って紹介します。

### 要件で「載せないもの」を先に決めた

機能要件と同時に「再生数などの統計は載せない」（作品を見せる場に数字は不要）という**載せないものの判断**を最初に確定しました。これが後の情報設計をシンプルにしてくれました。

### データは既存の情報源から抽出した

手打ちのCSVを用意する案もありましたが、既存の情報源からの抽出に切り替えました。

- **noteマガジン** 記事からタイトル・キャラ名・シリーズ・投稿日・サムネイル・クレジット・使用エフェクトを抽出
- **ニコニコのアカウントページ**からプロフィールアイコンと自己紹介を取得
- **YouTube** は oEmbed 経由でタイトルを解決

:::details 用語メモ：noteマガジン
記事をテーマ別にまとめられるnoteの機能です。自分の場合、MMD動画の制作解説記事を1本ずつ書いて1つのマガジンに集約しており、これが今回のデータ抽出の主要な情報源になりました。

[マガジンとは – noteヘルプセンター](https://www.help-note.com/hc/ja/articles/360000383501-%E3%83%9E%E3%82%AC%E3%82%B8%E3%83%B3%E3%81%A8%E3%81%AF)
:::

この時点でデータを `videos.js` に分離した構造体として持たせ、未取得の項目は `null` にして**あるものだけ描画する**設計にしました。段階的にデータが埋まっていく前提のサイトなので、この方針には最後まで助けられました。

### デザインは2案比較で決めた

「ライト系でクリーン」という要望に対してクリーン版とポップ版の2案を並べ、採用したのはクリーム色の背景＋太い黒枠＋ハードシャドウの**ポップ版**。1案だけ見せられると「これで良いか」しか判断できませんが、2案並ぶと**なぜそちらか**が言語化されます。

![案1 クリーン版](https://static.zenn.studio/user-upload/8516b422a961-20260725.png)

![案2 ポップ版](https://static.zenn.studio/user-upload/be052bea39d0-20260725.png)

### 埋め込みプレイヤーの罠はこの段階で踏んでいた

デザインツール上でプレビューを触っていた段階で、実装に直結する罠を2つ踏みました。

1. **YouTube埋め込みがエラー153で再生不能** → iframe に `referrerpolicy="origin"` を付与して解決
2. **ニコニコの埋め込みプレイヤーは横型固定** → 縦型ショートを9:16の枠に収めると再生画面が半分になる。ニコニコタブは常に16:9、YouTubeタブのみ9:16に切り替える設計に

この2つをハンドオフ README に「罠」として明記して引き継いだため、Claude Code 側の再実装では同じ問題を一度も踏み直しませんでした。**ハンドオフ資料には仕様だけでなく「ハマった記録」を書く**のが、環境をまたぐ開発では有用かと思います。

## Claude Code編：公開までの約1時間

デザインとデータが固まったところで Claude Code に移行。最初の指示は「GitHub Pages へデプロイ＆運用する前提の設計で全体を再実装してほしい。やることが多そうなので、Issue化してフェーズを分け段階的に対応を進める形でもOK」でした。

Claude Code はロードマップ文書と GitHub Issues を対応付けてフェーズ分けし、Phase 1（データ基盤）→ Phase 2〜3（サイト本体）→ Phase 4（Pages公開）を**約1時間で完走**しています。

![GitHub Issuesの一覧](https://static.zenn.studio/user-upload/f2af01dd62a4-20260726.png)

なお GitHub Pages × GitHub Actions の静的サイト構成は、以前コミュニティポータルサイトを構築した際の型をそのまま踏襲しています。

https://zenn.dev/easy_easy/articles/89318e4d0acb4f

### Phase 1：正データと生成物を分離するデータ基盤

ハンドオフされた `videos.js`（1ファイルに全動画分の構造体）を、そのまま使わず **1動画=1YAMLファイル**（`data/videos/<id>.yaml`）に分解しました。

```yaml
id: addiction
title: '[A]ddiction'
chara: イヴリン
series: ゼンゼロ
date: '2026-01-05'
nico: sm45803776
yt: gc_9E1KsCHY
note: https://note.com/unsoluble_sugar/n/nd20f63ff7b4e
thumb: https://assets.st-note.com/production/uploads/images/...
credits:
- 楽曲：[A]ddiction / GigaReol×EVO+様
- 振付：足太ぺんた様
- モーション：hino様
- カメラ＆背景＆PVキット：MAO様
- モデル：miHoYo / 观海子様
- エフェクト：そぼろ様 / くろくま様 / カヤ様 / びーと様 / 針金P様 / P.I.P様
effects:
- ExcellentShadow2
- くろくまトゥーン
- A-Toon2
- B-ToonShader
- HgSAO
- WorkingFloorAL
- PostRimLightToon
tags:
- ゼンゼロ
- イヴリン
```

このYAML群が、手動編集の対象となる唯一の元データ＝**正データ**となります。

![](https://static.zenn.studio/user-upload/a2c143327d90-20260726.png)

![](https://static.zenn.studio/user-upload/9c3491f4414a-20260726.png)

サイト本体が読むのは `build_data.py` が YAML群から生成する `js/videos.gen.js` で、**生成物は直接編集禁止**。さらに pre-commit hook で `build_data.py --check` を走らせ、**YAMLと生成JSが不整合のままではコミットできない**ようにしました。

```bash
python3 scripts/build_data.py          # data/*.yaml → js/videos.gen.js 再生成
python3 scripts/build_data.py --check  # 同期検査（pre-commit / CI 用）
```

1動画=1ファイルにしたのは、後述の抽出ツールが動画単位で補完する際に差分が読みやすく、コンフリクトも起きないからです。手動編集の対象を「正データのYAMLだけ」に限定したことで、以降のデータ作業で生成物を壊す事故はゼロでした。

### Phase 2〜3：ハンドオフHTMLの「コピー」ではなく「再実装」

サイト本体は Vanilla JS で書き直しました。フレームワークを使わなかったのは、一覧と詳細モーダルだけの小規模なサイトで、今後大きな機能追加も入らない想定だからです。依存パッケージのバージョン追従や定期的な更新作業が発生せず、メンテナンスコストはほぼゼロ。ビルド工程が無いので、GitHub Pages にファイルを置くだけで動く構成とも相性が良いです。

:::details 用語メモ：Vanilla JS
フレームワークやライブラリを使わない素の JavaScript のこと。語源や由来はこちらの記事が詳しいです。

https://zenn.dev/seya/articles/66809b3d59151c
:::

ハンドオフのHTMLをコピーして継ぎ足すのではなく、`mp-` プレフィックスのCSS設計、app（状態）/ render（一覧描画）/ modal（詳細モーダル）の責務分離という構成で、**同じ見た目を対象環境の作法で再実装**しています。

再実装直後のローカル実機確認では、デザインツール内では気づけない実装バグがいくつか見つかりました。

- モーダルを閉じても **iframe の動画が再生され続ける**
- モーダル開閉時に **背後のグリッドが再描画されてちらつく**
- 無限スクロールの **追加読み込み時にちらつく**

いずれも「詳細ダイアログ開く際に裏側で画面の読み込み走ってる？」のような**現象ベースの短い指示**を投げ、原因特定と修正は Claude Code 側という分担で潰しています。この「実機で触る→現象を口頭で伝える→直る」の高頻度ループが、今回の品質を作った実感があります。

ただしこれは「今回くらいの規模だから人間が確認役に入るループが早い」という話です。検証すべき画面や状態が多い開発でAIに自走させるなら、AIが自分でテストを実行・検証できる基盤を先に組むほうが良いと思います。

仕事のゲーム開発でE2Eテスト基盤を整えてAIに回させた記録を書いているので、気になる方はご参考ください。

https://zenn.dev/unsoluble_sugar/articles/2a1f9e08ac9980

https://zenn.dev/unsoluble_sugar/articles/57d4ca55ef1ef1

### Phase 4：デプロイ成果物に「載せるものだけ」を列挙

GitHub Actions で `_site/` ディレクトリを組み立てて Pages に公開する構成です。成果物には**載せるものだけを明示的にコピー**します。

| 区分 | 対象 |
|---|---|
| 含める | `index.html`・`styles.css`・`js/`・favicon類・OGP画像・`.nojekyll` |
| 含めない | `data/`（正データYAML）・`scripts/`（Pythonツール）・`docs/`（設計ドキュメント）・`design/`（デザインハンドオフ） |

リポジトリの全ファイルを配信する branch デプロイと違い、公開するファイルを明示的に制御できます。

## ここからが本番：データ140件との格闘

公開まで約1時間で走り切ったあと、開発時間の大半を費やしたのはデータ整備でした。ここからが本記事の本題です。

### 未登録データの自動発掘

ハンドオフ時点で登録されていた動画は50件。ここで「未登録の動画がまだたくさんあるはず。50件ですべてではない」と伝え、noteマガジン108記事・ニコニコマイリスト127件・YouTubeプレイリスト128件のURLを渡しました。

:::details 補足：各プラットフォームの本数と登録140件が一致しない理由
使用する素材コンテンツの規約上ニコニコでしか公開できない動画や、60FPS版を独立してYouTubeにアップしている動画があるため、両プラットフォームの内容は完全なミラーではなく本数に差分があります。また、投稿初期の動画については制作解説のnote記事を書けていないため、note記事の本数も動画数とは一致しません。
:::

Claude Code は `scripts/enrich/` 配下に note / nicovideo / youtube の3つの抽出ツールを実装。マイリストと `data/videos/` を突き合わせて**未登録90件のYAML雛形を機械的に生成**（`nicovideo.py scaffold`）し、各動画の概要欄・note記事から投稿日やクレジットを補完して、最終的に**140件**まで拡充しました。

```bash
python3 scripts/enrich/nicovideo.py scaffold  # マイリストにあるが未登録の動画のYAML雛形を生成
python3 scripts/enrich/nicovideo.py match     # マイリスト/公式シリーズ照合 → 投稿日・シリーズ等を補完
python3 scripts/enrich/note.py match          # noteマガジン記事一覧とタイトル照合 → 解説記事URLを補完
python3 scripts/enrich/note.py fetch          # note記事本文 → クレジット・エフェクトを補完
```

ハンドオフ時点のデータは「初期値」と割り切り、**正データはローカル環境で一括再構築**した方が速い、というのが今回の結論です。90件の発掘を手作業でやるのは現実的ではありません。

抽出ツールは全コマンド共通で**既存値は上書きせず null のフィールドのみ補完する**仕様にしています。手で直した値がツールの再実行で戻る事故を防ぐためです。

### 誤紐付けの対応

自動照合には落とし穴もありました。**同じ楽曲の動画を別キャラで投稿**しているケースがあるため、タイトルだけの照合でnote記事が別の動画に誤紐付けされる事故が発生したのです。

対策として、照合時に**候補が1件でも必ずキャラ名を突き合わせる**共通処理 `pick_by_chara` を実装し、プロジェクトドキュメントの「ハマりどころ」にも明文化しました。

> **同一楽曲・別キャラの動画が複数ある**ことが多い（例:「ロキ」「ダーリンダンス」を異なるキャラで複数回投稿）。note記事・マイリストとのタイトル照合は**候補が1件でも必ずキャラ名で照合すること**。候補1件だから安全、とは限らない

自動抽出は「埋まらない」より「**間違って埋まる**」ほうが怖いです。事故のたびに検証ルールをツールとドキュメントの両方に落とし込んでいくことで、同種の誤りは再発しなくなりました。

なお、この手の知見をなんでも `CLAUDE.md` に書き足していくと肥大化する一方なので、`.claude/rules/` や `.steering/` などの参照用ドキュメントに寄せて、`CLAUDE.md` 側は要点と参照導線に留めるのが無難だと思います。

ルールによるワークフロー規約の構成などは、以下の記事を参考にしてください。

https://zenn.dev/unsoluble_sugar/articles/beaac7bbf9ee7a#%E3%83%AB%E3%83%BC%E3%83%AB%E3%81%AB%E3%82%88%E3%82%8B%E3%83%AF%E3%83%BC%E3%82%AF%E3%83%95%E3%83%AD%E3%83%BC%E8%A6%8F%E7%B4%84

### コンテンツツリー照合によるエフェクト補完

note記事を書いていない動画の使用エフェクト情報については、ニコニコの**コンテンツツリー**（親作品の登録情報）の登録名と既知エフェクト語彙を照合し、**一致した場合のみ補完する** `nicovideo.py tree` ツールの実装で解決しました。

MMD導入時の名称と乖離のある曖昧な配布物名の解決は、**人間が対訳表を渡し、AIが照合を回す**形で対応。「ドメイン知識の供給は人間」「突き合わせの実行はAI」という役割分担です。

それでも残った欠損は「情報源（note記事・ツリー登録）が存在しない恒久的な欠損。誤った値を入れるより null のまま」と方針を明文化しました。null の項目はUIごと非表示になる設計なので、無理に埋める必要はありません。

**欠損を null で残す勇気**も、データポータルには必要だと思います。

これはあくまで「自動抽出で誤った値を入れない」ための線引きです。正データはYAMLに1行足すだけなので、時間に余裕のあるときに記憶や手元の資料を頼りに手動で埋めていく余地は残っています。

### 方針転換は「データの正」と「表示の優先」に分解する

デザイン期は「ニコニコとYouTube両方にある場合はニコニコ側の情報を主体にする」で統一していましたが、運用してみると埋め込み再生の体験はYouTubeのほうが良く、詳細モーダルの**初期タブとタブ並びをYouTube優先に転換**しました。

![](https://static.zenn.studio/user-upload/a7a49b6f3fe7-20260726.png)

## スマホ実機確認でしか出ない問題たち

モバイル対応で踏んだ問題は、どれもデスクトップブラウザのレスポンシブモードでは再現しないものでした。

- iOSで「▶」の文字が**絵文字グリフに置換**されてレイアウトから浮く → SVGアイコン化で解決
- ヘッダーのSNSボタンが2段に折り返す → モバイルは「@」ボタン1つに集約
- モーダルで動画再生中に背後をスクロールすると**動画が止まる**（裏で再描画が走っていた）
- 縦型ショートのレールはモバイルではデフォルト折りたたみに（タップで開閉）

特に絵文字グリフ問題は、テキストの「▶」がiOSの実機でだけカラー絵文字に化けるという、知らないと原因特定に苦労するやつです。**装飾的な記号はテキストではなく、SVGで描画するか画像で持たせる**のが無難です。

## 継続運用の型ができて一周

作って終わりではなく、新規投稿を取り込む運用サイクルまで整えました。

```text
新しい動画を投稿 → note解説記事を書く
  → scripts/enrich/*.py match → fetch   （URL照合・情報補完）
  → build_data.py                       （生成JSを再生成）
  → コミット & push → Actions が自動デプロイ
```

実際に開発の最終日、前日投稿した動画について「note記事を書いたので不足情報を補完して」と伝えるだけで、照合→補完→再生成→デプロイまで一周しました。

**運用が続くかどうかは、この追従の手軽さで決まる**気がします。

## 学び・ハマりどころまとめ

1. **デザインツールと開発環境の分担が機能した**。見た目の意思決定は Claude Design、Git・CI・一括データ処理は Claude Code。ハンドオフ資料に「罠」を書き残したことで再実装での踏み直しゼロ
2. **YouTube埋め込みのエラー153は `referrerpolicy="origin"` で解決**。ニコニコの埋め込みは横型プレイヤー固定なので、縦型ショートでも16:9で扱う（記事執筆時点の仕様）
3. **正データ（YAML）と生成物（JS）を分離し、pre-commit で同期を強制**。手動編集事故を仕組みで防ぐ
4. **データは「発掘→補完→検証」をツール化**。90件の発掘は手作業では現実的でなかった。抽出ツールは「既存値を上書きせず null のみ補完」に
5. **自動抽出には検証ルールが要る**。「候補が1件だから安全」とは限らない。事故のたびにルールをツールとドキュメントの両方へ明文化（CLAUDE.mdの肥大化は避け、rules等の参照用ドキュメントに寄せる）
6. **欠損は null で残す勇気**。自動抽出では情報源のない項目を無理に埋めず、UIごと非表示にする設計とセットで成立させる。時間のあるときに手動で埋める余地は残る
7. **方針は「データの正」と「表示の優先」に分解して転換する**。後から片方だけ変えられる
8. **実機確認の往復が品質を作る**。iOSの絵文字グリフ置換のような問題は実機でしか出ない。指示は現象ベースの短文で十分、原因特定はAIに任せる
